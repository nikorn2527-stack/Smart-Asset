## 1. System Overview

ITAM-NextJS is a single Next.js 16 / TypeScript / Prisma application that replaces three legacy Google Apps Script apps (ITAM / Services / Stock). It is deployed on Vercel (region `sin1`, see `vercel.json:18`) against a Supabase Postgres database (auto-switched to transaction-mode pooler port 6543 to bypass the 15-connection Free-tier limit, see `src/lib/db.ts:62`). The codebase is one monolithic app — there is no separate technician app, no separate public app, no separate admin app. Mobile + public + staff all share the same Next.js app, same JWT auth, same Prisma client, same DB.

Stack highlights (see `package.json`):
- Next 16.1, React 19, TypeScript 5
- Prisma 6.19 (PostgreSQL provider, `prisma/schema.prisma:9`)
- shadcn/ui (New York style) + Tailwind 4 + Radix primitives
- Auth: bcryptjs + jose (JWT) + WebAuthn (`@simplewebauthk`) + OAuth (Google/Apple/LINE via `next-auth`-style custom JWT)
- External integrations: `google-spreadsheet`/`googleapis`, `@aws-sdk/client-s3` (for Cloudflare R2), `@vercel/blob`, `@vercel/edge-config`, `@vercel/kv`, `@supabase/supabase-js`, `nodemailer`, `resend`, `tesseract.js` (OCR), `jsqr` (QR decode), `sharp` (image processing)
- Build: `next build --webpack` (Turbopack disabled for build), standalone output only when self-hosted (`next.config.ts:21`)

The app exposes ~250 API routes under `/src/app/api/`, ~60 React components under `/src/components/itam/` (desktop) + `/src/components/itam/mobile/` (mobile) + `/src/components/public/` (public QR flow), and ~80 helper modules under `/src/lib/`.

## 2. Work Order Lifecycle — the central nervous system of the app

### 2.1 Status state machine

The `WorkOrder.status` column (`prisma/schema.prisma:288`) is a free-text string but the canonical allowed values are enforced in `src/app/api/work-orders/route.ts:19-25`:

```
PENDING → IN_PROGRESS → WAITING_PARTS ⇄ IN_PROGRESS → COMPLETED
   ↓                                ↓
   └────────────────────────────────┴→ CANCELLED
```

The new public QR flow introduces **`PENDING_REVIEW`** for Tier 2/3 submissions (`src/app/api/public/repairs/route.ts:401`) — **but this status is NOT in the `VALID_STATUSES` allowlist** of the main WO route (`src/app/api/work-orders/route.ts:19-25`), which means GET filters by status will silently drop PENDING_REVIEW WOs. This is an open bug. See §8.

### 2.3 Assignment flow

**Endpoint**: `POST /api/work-orders/[id]/assign` — `src/app/api/work-orders/[id]/assign/route.ts`

**Auth**: `loadAuthorizedWorkOrder(req, id, 'WO_ASSIGN')` — Site-scoped permission check via `AuthorizationContext.canAtSite(woSite, 'WO_ASSIGN')` (`src/lib/wo-authz.ts:143`). Superadmin bypasses.

**Fields mutated** (`src/app/api/work-orders/[id]/assign/route.ts:71-81`):
- `assignedTo` = body.assignedTo (technician name, free-text)
- `assignedBy` = `auth.user.email` (never trusted from body)
- `assignedAt` = `new Date()`
- `assignmentNote` = body.assignmentNote (optional)
- `status` = auto-advances `PENDING → IN_PROGRESS` (only on first assignment; preserves WAITING_PARTS etc.)

**Side effects**:
- Creates a `WorkOrderMessage` with `authorRole='admin'`: `มอบหมายช่าง: ${tech} — ${note}` (L83-90)
- Audit log `WO_ASSIGN` (L92-99)
- **Notification** (`src/app/api/work-orders/[id]/assign/route.ts:104-115`): calls `notifyWorkOrderAssigned` → `sendLINE(message, wo.lineUserId ?? admin_group)` + `sendTelegram(...)`. Goes to the assigned technician if `wo.lineUserId` is known — but in practice, `wo.lineUserId` is the REPORTER's LINE ID, not the technician's, so this actually notifies the reporter that their WO was assigned. ⚠️

**V1 equivalent** (`src/app/api/v1/work-orders/[id]/assign/route.ts`): same field mutations, but **no notification trigger**. Sets `acceptStatus='accepted'` too.

### 2.5 Photo attachments

**Two parallel storage mechanisms exist**:

1. **Legacy single-image fields** on `WorkOrder` (`prisma/schema.prisma:285-287`):
   - `picBefore`, `picOnsite`, `picAfter` — each is a `String?` column
   - Stored as base64 data URL strings directly in the WO row
   - Used by: V1 endpoints, some legacy code paths

2. **Multi-image table** `WorkOrderImage` (`prisma/schema.prisma:388-404`):
   - `stage: 'before' | 'onsite' | 'after'`
   - `image_data: String` — base64 data URL, **capped at 1.5MB per image** (`src/app/api/work-orders/[id]/images/route.ts:40`)
   - Max 12 images per stage (`STAGE_CAP = 12`, L175)
   - Used by: main `/api/work-orders` route (mirrors picBefore into WorkOrderImage rows on create, L627-651), the mobile app, and the detail page

**Upload mechanism**: The technician's `MobileMyWork` component captures a photo via `navigator.mediaDevices.getUserMedia({ video: { facingMode: 'environment' }})` (`mobile-my-work.tsx:1544-1552`), draws it to a canvas at 1024px max width, then `canvas.toDataURL('image/jpeg', 0.7)` (`mobile-my-work.tsx:1590-1597`) → base64 string is sent in JSON to `POST /api/work-orders/[id]/images`.

**Where the photos are stored**: ❗ **In the database as base64 strings.** Not in Cloudflare R2, not in Vercel Blob, not in Supabase Storage.

The `src/lib/r2-storage.ts`, `src/lib/vercel-blob-storage.ts`, `src/lib/supabase-storage.ts`, and the unified `src/lib/storage.ts` abstraction DO exist and are well-documented — but a Grep for `from '@/lib/r2-storage'`, `from '@/lib/vercel-blob-storage'`, `from '@/lib/supabase-storage'`, and `from '@/lib/storage'` finds **ZERO import sites outside the libs themselves**. The storage abstraction is dead code waiting to be wired in. Photos bloat the Postgres DB.

### 2.6 Completion / closure

**Endpoint**: `POST /api/work-orders/[id]/complete` — `src/app/api/work-orders/[id]/complete/route.ts` (467 lines — the most complex WO route).

**Auth**: `loadAuthorizedWorkOrder(req, id, 'WO_COMPLETE')` — Site-scoped.

**Body accepted**:
```ts
{
  note?: string,           // appended to detailsAdmin
  picAfter?: string,       // base64 data URL
  picOnsite?: string,      // base64 data URL
  resolution?: string,     // free-text resolution description
  resolutionGroup?: string, // taxonomy group for the resolution
  parts?: Array<{ productCode, quantity, remark? }>,
  autoApproveParts?: boolean
}
```

**Validation**: `validateRepairCompletionInput` from `src/lib/repair-completion-contract.ts` (input-shape contract).

**Parts sub-flow** (Step 2 — `complete/route.ts:118-347`):
- For each part in `parts[]`: look up StockItem by productCode, validate qty > 0 and active
- If `autoApproveParts=true`: create APPROVED StockTransaction (type=OUT), decrement StockItem.quantity, allow WO to complete in this request
- If `autoApproveParts=false`: create PENDING StockTransaction, flip WO to `WAITING_PARTS`, return early WITHOUT completing (L328-346)
- Block completion if any PENDING StockTransactions exist for the WO (L358-385) — `qty=0` (open-bottle usage) is auto-skipped

**Completion mutation** (`complete/route.ts:394-408`):
```ts
data: {
  status: 'COMPLETED',
  workCompletedAt: now,
  closedAt: now,
  picAfter: normalizedPicAfter ?? wo.picAfter,
  picOnsite: normalizedPicOnsite ?? wo.picOnsite,
  resolution: resolutionTrim || null,
  resolutionGroup: resolutionTrim ? (resolutionGroupTrim || null) : null,
  detailsAdmin: normalizedNote ? (wo.detailsAdmin + '\n' + normalizedNote) : wo.detailsAdmin,
}
```

**Side effects**:
- Creates `WorkOrderMessage` with `authorRole='admin'`: `ปิดงานเรียบร้อย — ผลการแก้ไข: ${resolution}` (L410-421)
- Audit log `WO_COMPLETE` (L423-434)
- **Notification** (`complete/route.ts:440-454`): calls `notifyWorkOrderCompleted` → `sendLINE(message, wo.lineUserId ?? admin_group)` + `sendTelegram(...)` to the reporter's LINE (if `wo.lineUserId` is set) — **THIS IS THE KEY QUESTION ANSWERED IN §3.2 BELOW**

**V1 equivalent** (`src/app/api/v1/work-orders/[id]/complete/route.ts`): same field mutations, **NO notification trigger**, NO parts handling. V1 is the stripped-down API for external apps.

## 3. LINE Integration (inbound + outbound)

| # | Channel | Purpose | Where configured | Direction |
|---|---|---|---|---|
| A | **LINE Messaging API (OA webhook)** | Receive repair reports from users via chat; push status notifications back to users | `AppSetting.line_channel_access_token` + `line_channel_secret` | Both directions |

### 3.1 INBOUND: LINE OA webhook → WorkOrder

**Endpoint**: `POST /api/line/webhook` — `src/app/api/line/webhook/route.ts` (741 lines)

**Signature verification** (L69-78, 306-331): HMAC-SHA256 of the raw body using `AppSetting.line_channel_secret`. In production, missing secret → reject (503). In dev, accept without verification (warns).

**Event types handled**:
- **`follow`** (L358-388): User added the bot. Send welcome message. Upsert `LineBinding` (records the LINE user exists, even before we know who they are).
- **`message.text`** (L390-707):
  - **Dedup** by `lineMessageId` (`WorkOrder.lineMessageId` is unique) — L398-408. If a WO already exists with this messageId, skip silently (LINE retries if no 200).
  - **Branch 1: status lookup** (L485-519) — text starts with `ติดตาม` / `สถานะ` / `status` → reply with the user's latest WO status.
  - **Branch 2: report keyword** (L521-537) — text is exactly `แจ้งซ่อม` / `แจ้ง` → reply with quick-reply menu.
  - **Branch 3: device code** (L539-633) — text matches a `Device.assetCode` or `serialNumber` (case-insensitive). If matched → create WO with device context, pull reporter info from `LineBinding` if it exists. Reply: `✅ สร้างใบงานแล้ว WO-XXXX ... เจ้าหน้าที่จะติดต่อกลับโดยเร็ว`.
  - **Branch 4: default** (L635-706) — text becomes WO subject. `LineBinding` lookup for reporter name/tel/employeeCode. Reply: `✅ สร้างใบงานแล้ว`.
- **`message.image`** (L411-471): Download image from LINE → `processLineImage` (`src/lib/line-image-handler.ts`) → try jsQR decode → if QR found, look up device → create WO. Fallback: Tesseract.js OCR on the image to read text labels.
- **`postback`** (L709-734): Template button clicks. Acknowledge + log.

**Reply mechanism**: `replyMessage(replyToken, messages, accessToken)` (L84-114) → POST `https://api.line.me/v2/bot/message/reply` with the same replyToken from the event. Only works within ~1 minute of the event.

**No `notifyWorkOrderCreated` is called** for LINE-originated WOs — the webhook uses the immediate reply mechanism instead. This is a deliberate design choice: the user gets instant feedback via reply, then later gets push notifications on assignment/completion.

### 3.3 The CRITICAL question: Does the system notify the original reporter when their WO is closed?

1. `AppSetting.line_channel_access_token` is configured (loaded by `loadSettings()` in `src/lib/notifications.ts:134-156`)
2. `AppSetting.notify_enabled !== 'false'` (L322)
3. `WorkOrder.lineUserId` is set on the closed WO — this is true for:
   - WOs created via LINE OA webhook (always set, see §3.1)

4. The reporter has added the LINE OA as a friend (otherwise LINE Push API returns 401)

If any condition fails, `sendLINE` logs the message to console and returns silently. There is no retry, no fallback to email/SMS.

## 6. Sites & Multi-tenancy

### 6.1 The TWO Site models

The app has two parallel Site models — this is intentional, reflecting the migration from the legacy Apps Script design:

| Model | Purpose | Where used |
|---|---|---|
| `Site` (`prisma/schema.prisma:513-524`) — **legacy** | Simple `code + name + address + phone` row. Used by sync-adapter for site allowlist. | `src/lib/sync-adapter.ts:74` (`db.site.findMany` to derive allowlist). Seeded with HQ, BKK-1, CNX, UDH, NKP (`prisma/seed.ts:40-48`). |
| `SiteAttribute` (`prisma/schema.prisma:477-508`) — **rich** | Per-site config: `SiteCode` (unique, FK target), `SiteName`, `LineOA` (LINE OA ID/handle per site), `Hotline`, `PaperRateBW`, `PaperRateColor`, `TelegramChatId`, `EmailAddress`, `LiffId`, `LiffAutoFriendLine`, `PublicRepairDailyLimit`, `PublicRepairIpDailyLimit`, `isDemo`. | All admin UI, public QR repair, paper analytics, sticker rendering. `SiteAttribute` is the canonical source. |

The relationship: `PublicReporter.siteCode` is an FK to `SiteAttribute.SiteCode` (L1396). `WorkOrder.siteCode` is a free-text column that should match a `SiteAttribute.SiteCode` (no FK enforced — Phase 0 transitional). `Device.site` is a free-text column too.

### 6.2 LINE OA per site

**Confirmed**: `SiteAttribute.LineOA` (`prisma/schema.prisma:481`) stores a per-site LINE OA identifier (free-text — likely the OA's LINE ID or bot handle). This is read by:
- `GET /api/public/devices/[shortId]` — returns `siteContact.lineOA` to the public device card UI (`src/app/api/public/devices/[shortId]/route.ts:174`)
- `SiteAttribute.LiffId` (L494) — the LIFF app ID if we deploy as an in-LINE app
- `SiteAttribute.LiffAutoFriendLine` (L495) — the LINE OA handle to auto-friend on login

⚠️ **Open question**: The `LiffAutoFriendLine` field is in the schema but I could not find code that uses it to actually issue a friend-add request after LINE Login. The auto-friend mechanism for Tier 1/2 reporters is documented in the schema comment but not implemented in code. This means Tier 1/2 reporters login via LINE Login but DON'T automatically friend the site's LINE OA — so the later `sendLINE(wo.lineUserId)` push on WO completion will likely fail with 401/403. See §8.

### 6.3 demoFilter — demo vs real data isolation

Implementation: `src/lib/demo-mode.ts`

The app supports a "demo mode" where demo users (staff testing the app) can do anything without polluting production data:

- `User.isDemo = true` → demo user
- All `User.isDemo` rows see ONLY data tagged `isDemo: true`
- All real users (`isDemo = false/null`) see ONLY data tagged `isDemo = false/null`
- Every model has an `isDemo Boolean @default(false)` column

Helpers:
- `demoFilter(user)` (L42-52): returns `{ isDemo: true }` for demo users, `{ OR: [{ isDemo: false }, { isDemo: null }] }` for real users. Spread into every Prisma `where` clause.
- `demoTag(user)` (L62-65): returns `{ isDemo: true }` for demo users, `{}` for real users (lets DB default apply). Spread into every Prisma `data` payload on create.
- `POST /api/itam/demo/reset` — deletes all rows where `isDemo = true`.

This means demo users can create devices, WOs, meter readings, stock items etc. without affecting real data, and the cleanup is one API call.

### 6.4 Site-scoped authorization (RBAC)

Phase 1 RBAC foundation: `src/lib/authorization-context.ts` + `src/lib/wo-authz.ts` (the WO-specific helper).

Flow:
1. `requireAuth(req)` — verifies JWT, returns `{ user, row, isDemo }`.
2. `buildAuthorizationContext(user, userId, allowedSites)` — loads `UserSiteGrant` rows; falls back to legacy `User.allowedSites` (comma-separated string or 'ALL') if no grants exist (audits each fallback). Returns `AuthorizationContext` with:
   - `grants: SiteGrant[]` (per-site role + permissions)
   - `siteScope: { kind: 'all' | 'sites' | 'none', siteCodes: string[] }`
   - `effectivePermissions: Permission[]` (union across all sites — DON'T use for action decisions)
   - `canAtSite(siteCode, perm)` — the canonical per-site permission check
   - `canAccessSite(siteCode)`, `roleAtSite(siteCode)`, `permissionsAtSite(siteCode)`
3. For WO routes: `loadAuthorizedWorkOrder(req, id, permission)` wraps the above + loads the WO + derives its site (`wo.siteCode ?? wo.device?.site`) + checks `canAtSite(woSite, permission)`. Returns 404 for both "not found" and "not authorized" to avoid leaking WO existence.

`superadmin` and `admin` global roles bypass all Site checks (`src/lib/wo-authz.ts:109`).

### 7.2 Tier system

| Tier | Trigger | phoneVerified | Initial WO status | Anti-spam | Notification routing |

### 7.3 What the new Public QR Repair system does that the existing system DOES

✅ **Same WorkOrder table** — public QR WOs land in the same `WorkOrder` table as staff/LINE/sync WOs.
✅ **Same `notifyWorkOrderCreated` trigger** on creation — pushed to LINE admin group + Telegram.
✅ **Same `notifyWorkOrderCompleted` trigger** on closure — pushed to `wo.lineUserId` (the LINE reporter, if Tier 1/2).
✅ **Same `notifyWorkOrderAssigned`/`notifyWorkOrderCancelled`** triggers when staff act on the WO.
✅ **Same `/wo/[woNumber]` tracking page** — public can scan/click to track status.
✅ **Rate limiting** (new): per-phone + per-IP daily caps that the existing system does NOT have for staff/LINE submissions.
✅ **Anti-spam** (new): `PublicReporter.isBlocked` lets staff ban a phone/LINE user.

### 7.4 What the new Public QR Repair system does NOT do that the existing system DOES (gaps)

❌ **Auto-friend the site's LINE OA** — `SiteAttribute.LiffAutoFriendLine` field exists but no code calls the LINE friend-add API after login. So `sendLINE(wo.lineUserId)` on WO completion will likely 401 if the reporter hasn't manually added the OA. The existing LINE webhook flow doesn't have this problem because the user's `follow` event IS the friend-add.
❌ **Immediate reply confirmation** — the LINE webhook flow replies instantly via `replyMessage(replyToken)` ("✅ สร้างใบงานแล้ว WO-XXXX"). The public QR flow shows a success screen in the browser, but does NOT push a LINE message at creation time — the user has to wait until they get home/closed notifications.
❌ **`PENDING_REVIEW` status** is set for Tier 2/3 submissions, but it's NOT in `VALID_STATUSES` (`src/app/api/work-orders/route.ts:19-25`). This means the main WO GET endpoint's status filter (`?status=PENDING_REVIEW`) will silently return zero rows. Staff UI status chips won't render PENDING_REVIEW. **The WO is created with status='PENDING_REVIEW' but staff can't filter for it.** This is a real bug.
❌ **V1 API parity** — public QR WOs are created via `/api/public/repairs`, NOT `/api/v1/work-orders`. So external billing apps pulling `/api/v1/work-orders?specialFee=true` will NOT see them. (They will see them via the main `/api/work-orders` GET, but only if the caller has VIEW_DEVICES perm and a matching Site scope.)
❌ **No webhook for Tier 2/3 review reminders** — when a `PENDING_REVIEW` WO sits untouched, there is no cron job to ping staff. The existing `notifyWorkOrderCreated` fires once at creation, then nothing until staff manually act.

These are findings the code review surfaced. Some are confirmed bugs; some are design decisions whose rationale isn't documented.

### 8.1 PENDING_REVIEW status not in allowlist

- **Confirmed bug.** `src/app/api/public/repairs/route.ts:401` sets `woStatus = phoneVerified ? 'PENDING' : 'PENDING_REVIEW'`, and the WO is created with `status: woStatus` (L594).
- `src/app/api/work-orders/route.ts:19-25` defines `VALID_STATUSES = new Set(['PENDING', 'IN_PROGRESS', 'WAITING_PARTS', 'COMPLETED', 'CANCELLED'])` — does NOT include `PENDING_REVIEW`.
- `if (status && VALID_STATUSES.has(status)) where.status = status` (L286) — so a `?status=PENDING_REVIEW` query parameter is silently dropped.
- The stats counter (`PENDING`, `IN_PROGRESS`, etc.) on the WO list response doesn't include `PENDING_REVIEW`.
- **Impact**: Staff cannot filter the WO list to find pending-review submissions. They have to know to look for them via the all-status view. The KPI strip on the work orders page will undercount.
- **Fix**: Add `PENDING_REVIEW` to `VALID_STATUSES` + `stats` map. Possibly also to the mobile-my-work.tsx filter chips.

### 8.2 LINE auto-friend not wired

- `SiteAttribute.LiffAutoFriendLine` (`prisma/schema.prisma:495`) is documented as "LINE OA handle to auto-friend on login" but a Grep for `LiffAutoFriendLine` finds it ONLY in the schema — no code reads or uses it.
- The LINE Login callback (`src/app/api/auth/line/callback/route.ts`) does NOT issue a friend-add request after setting the `line_session` cookie.
- **Impact**: When a Tier 1/2 public reporter submits a repair and the staff later closes the WO, `notifyWorkOrderCompleted` calls `sendLINE(message, wo.lineUserId)` — but the user hasn't friended the OA, so LINE returns 401/403. The push silently fails (logged to console only).
- **Fix options**:
  1. Use LINE's friend-add URL (`https://lin.ee/{shortUrl}` or `https://page-line.me/{lineId}`) as a redirect after the LINE Login callback, with a UI prompt: "เพิ่มเพื่อนกับแอดมินเพื่อรับสถานะใบแจ้งซ่อม".
  2. Use a LIFF app instead of LINE Login — LIFF runs inside LINE, and you can issue a friend-add via the LIFF `liff.init()` + `liff.openWindow({ url: 'https://line.me/R/oaMessage/{lineId}/' })`.
  3. Manually prompt the user with a QR code to add the OA — non-automatic but reliable.

### 8.3 Storage abstraction is dead code

- `src/lib/r2-storage.ts`, `src/lib/vercel-blob-storage.ts`, `src/lib/supabase-storage.ts`, `src/lib/storage.ts` are all fully implemented (env-var detection, upload/download/delete, presigned URLs) — but a Grep finds ZERO call sites outside the libs themselves.
- Actual photo storage: base64 data URLs in `WorkOrderImage.image_data` (text column, 1.5MB cap per image, 12 images per stage).
- **Impact**: The DB will bloat over time. Each WO with 3 stages × 3 photos × ~700KB JPEG = ~6MB per WO in Postgres. At 1000 WOs that's 6GB — well past Supabase Free 500MB limit. The migration plan is documented in the r2-storage.ts header but no route uses it yet.
- **Fix**: Wire `/api/work-orders/[id]/images` to use `uploadImage()` from `src/lib/storage.ts` instead of writing base64 to the DB. Store the returned URL in `WorkOrderImage.image_data` (rename column or keep it as URL string).

### 8.4 `notifyPartsApproved` is orphaned

- Defined at `src/lib/notifications.ts:692` — well-formed, calls `sendNotification({ template: 'parts_approved', ... })`.
- A Grep for `notifyPartsApproved` finds ZERO call sites outside the file itself.
- The `/api/work-orders/[id]/parts/[txnId]/approve` route exists but does not call `notifyPartsApproved`. Likely an oversight.

### 8.5 V1 endpoints are notification-silent

- `POST /api/v1/work-orders` — no `notifyWorkOrderCreated`.
- `POST /api/v1/work-orders/[id]/assign` — no `notifyWorkOrderAssigned`.
- `POST /api/v1/work-orders/[id]/complete` — no `notifyWorkOrderCompleted`.
- This is **intentional** per the V1 contract (used by external apps that don't want notification side effects). But it means a WO created/assigned/completed via V1 will NOT trigger the LINE/Telegram push. If the same WO is later viewed by an end-user expecting a notification, they'll be disappointed.
- Documented in the V1 route comments? No — the rationale isn't in the code, just inferred from the missing calls.

### 8.6 `notifyWorkOrderAssigned` pushes to the reporter, not the technician

- `notifyWorkOrderAssigned` at `src/lib/notifications.ts:544` passes `lineUserId: wo.lineUserId` — that's the REPORTER's LINE user ID, not the assigned technician's.
- The intent (per the comment at L541) is "Notify the assigned technician of a new assignment." But the push goes to the reporter.
- **Impact**: When a staff member assigns a WO, the REPORTER gets a LINE message saying "📋 มอบหมายงาน WO-XXX — มอบหมายให้: {tech name}". The technician doesn't get any direct notification — they have to refresh their mobile "งานของฉัน" list.
- **Fix**: Look up the technician's `User.lineUserId` (if the technician is a registered user with linked LINE account) and push to that. Fall back to admin group if not found.

### 8.7 No retry queue for failed LINE pushes

- `sendLINE` catches all errors and logs them (`src/lib/notifications.ts:344-351`). The notification is recorded as "sent with error" in `AuditLog.detail.error` — but there's no retry.
- If LINE returns 429 (rate limit) or 401 (user unfriended), the push is lost.
- **Fix**: Add a notification queue (Vercel KV list or DB-backed `NotificationQueue` table) with retry-on-failure and dead-letter handling.

### 8.8 `google-service-account.json` committed to repo

- The file exists at `/home/z/my-project/google-service-account.json` — it's a real Google Service Account key, presumably for Sheets API access.
- Committing service account keys is a security smell. If this repo is public or shared, the key should be rotated and moved to env vars / Vercel secrets.
- Note: I did NOT read the file contents (out of scope for this audit) — just confirmed its presence.

### 8.9 LINE webhook signature verification fail-open in dev

- `src/app/api/line/webhook/route.ts:308-318`: if `line_channel_secret` is not configured, the webhook accepts requests without signature verification in non-production mode. This is documented as "DEV MODE ONLY" but if someone deploys with `NODE_ENV !== 'production'` and a missing secret, attackers can forge webhook events.
- The production check at L309-315 does reject when `NODE_ENV === 'production'` and secret is missing — but the dev fail-open is still a risk in preview environments.

### 8.10 Public reporter phone uniqueness is per-site, not global

- `PublicReporter` has `@@unique([siteCode, phone])` and `@@unique([siteCode, lineUserId])` (`prisma/schema.prisma:1399-1400`).
- This means the same phone number can be a reporter at multiple sites — which is intentional (per the comment at L1360-1361).
- But: the rate limit check at `src/app/api/public/repairs/route.ts:524-540` filters by `siteCode + reporter.phone`, so a user can submit 3 repairs per site per day = 3 × num_sites total. If there are 5 sites, that's 15 repairs/day from one phone. This is probably fine but worth documenting.

### 8.11 Unclear: Is the daily-report cron actually delivering value?

- `src/app/api/cron/daily-report/route.ts` (199 lines) aggregates yesterday's metrics into a JSON blob and... mostly just audit-logs it. The email send path is stubbed. The notification push isn't called.
- Vercel Hobby tier limit is 2 cron jobs (the daily-report route header at L18 says this is the 2nd, after keepalive) — but `vercel.json` declares 3 crons (`sync-legacy` being the 3rd). On Hobby tier, the 3rd cron will be ignored by Vercel.
- **Open question**: is the team on Vercel Pro (which supports unlimited crons) or Hobby? If Hobby, `sync-legacy` doesn't run.
