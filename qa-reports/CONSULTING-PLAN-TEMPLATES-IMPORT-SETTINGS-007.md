## 1. เทมเพลตและตัวแปร (Template Variable Coverage) — 🏷️ ✅ แก้แล้ว (ยืนยัน 2026-09-07)

### 1.1 อาการที่เจอ
ผู้ใช้ (เจ้าของระบบ) รู้สึกว่าปรับแต่งเทมเพลตยาก ตัวแปรไม่ครอบคลุม

### 1.2 สาเหตุที่ยืนยันจากโค้ด
ตัวแปรที่ใช้งานได้ในเทมเพลตถูกกำหนดและใช้งานผ่าน 3 ชั้นที่ต้องแก้พร้อมกัน:

1. **`src/lib/template-editor.ts`** — `TEMPLATE_VARIABLES` (รายการที่โชว์ใน picker UI) และ `TemplateRenderData` (TypeScript interface กำหนดว่ามีฟิลด์อะไรได้บ้าง) และ `SAMPLE_DATA` (ข้อมูลตัวอย่างตอน preview)
2. **`src/app/api/templates/[id]/render/route.ts`** — จุดที่ดึงข้อมูลจริงจาก `wo.device.*` มาแทนที่ตัวแปร (ปัจจุบันดึงแค่ assetCode/brand/model/serialNumber/name)
3. Device model จริงใน `prisma/schema.prisma` มีฟิลด์ที่มีประโยชน์แต่ไม่ถูกเปิดใช้ เช่น:
   - `type`, `status` (สถานะปัจจุบัน)
   - `warrantyEnd`, `purchaseDate`, `purchasePrice`, `vendor`, `contractNo` (ใช้ทำเอกสารครุภัณฑ์)
   - `ip`, `mac` (ใช้ทำป้าย IT asset)
   - `currentAssignee` (ผู้ใช้งานปัจจุบัน — สำคัญมากสำหรับสติกเกอร์)
   - `floor`, `room`, `costCenter`, `deviceGroup`

### 1.3 แนวทางแก้ (Methodology)

**ขั้นตอนที่แนะนำ — ทำทีละกลุ่มฟิลด์ ไม่ทำทีเดียวทั้งหมด เพื่อลด risk ของการพัง template เดิมที่มีอยู่:**

1. **จัดกลุ่มความสำคัญของฟิลด์ที่ขาด** (คุยกับทีมหน้างานว่าใช้ตัวไหนบ่อยสุด) ตัวอย่างการจัดกลุ่ม:
   - กลุ่ม "ต้องมีเร็วสุด": `warrantyEnd`, `currentAssignee`, `status`, `type`
   - กลุ่ม "ใช้ทำเอกสารครุภัณฑ์": `purchaseDate`, `purchasePrice`, `vendor`, `contractNo`
   - กลุ่ม "IT asset label": `ip`, `mac`, `floor`, `room`
2. **เพิ่มทีละกลุ่มใน 3 ชั้นพร้อมกันเสมอ** (เพิ่มใน `TEMPLATE_VARIABLES` แต่ไม่เพิ่มใน render endpoint จะทำให้ user เลือกตัวแปรได้แต่ print ออกมาว่าง — ต้องเช็คให้ตรงกันทุกครั้ง)
3. **เพิ่ม type safety กันหลุด**: ปัจจุบัน `TemplateRenderData` เป็น optional string ทั้งหมด แนะนำเขียน unit test เทียบ `Object.keys` ของ `TEMPLATE_VARIABLES` กับ keys ของ `TemplateRenderData` ให้ตรงกันเสมอ (กัน "ลืมเพิ่มอีกชั้น" ในอนาคต)
4. **Sample data ต้องอัปเดตคู่กัน** ทุกครั้งที่เพิ่มตัวแปรใหม่ ต้องเติมค่าใน `SAMPLE_DATA` ด้วย ไม่งั้นปุ่ม Preview จะโชว์ค่าว่าง/undefined

### 1.4 ความเสี่ยงที่ต้องระวัง
- เทมเพลตเก่าที่ลูกค้าสร้างไว้แล้วจะไม่ได้รับผลกระทบ (เพราะเป็นการ "เพิ่ม" ตัวแปรใหม่ ไม่ใช่เปลี่ยนของเดิม) แต่ควรทดสอบ regression กับเทมเพลตที่มีอยู่จริงในระบบก่อน deploy
- ฟิลด์ `warrantyEnd` เป็นวันที่ ต้อง format ให้ตรงกับ locale ไทย เหมือนฟิลด์ `date`/`printDate` ที่มีอยู่แล้ว (ใช้ `toLocaleString('th-TH')` แบบเดียวกัน)

### 1.5 ประมาณการความยาก
งานระดับกลาง-ต่ำ ไม่ต้องแก้ schema ฐานข้อมูล (ข้อมูลมีอยู่แล้วใน DB) เป็นแค่การ "เปิดท่อ" ข้อมูลที่มีอยู่แล้วให้ไหลไปถึง template — ทำได้ทีละ PR เล็กๆ ต่อกลุ่มฟิลด์

## 2. นำเข้าข้อมูล (Data Import) — 🏷️ Phase A ✅ แก้แล้ว / Phase B ⚠️ แก้บางส่วน

### 2.1 อาการที่เจอ
ผู้ใช้รู้สึกว่านำเข้าข้อมูลยังมีปัญหา ไม่สมบูรณ์

### 2.2 สาเหตุที่ยืนยันจากโค้ด — พบ 3 endpoint ที่ทำงานซ้ำซ้อนกัน

| Endpoint | บรรทัด | ใครเรียกใช้ | มี Transaction? | คุณภาพโครงสร้าง |
|---|---|---|---|---|
| `/api/import` | 2,336 | `import-page.tsx` (หน้า Import หลัก) + `legacy-import-section.tsx` | **❌ ไม่มี** | รวมหลาย entity (device/stock-in/stock-out) ไว้ไฟล์เดียว |
| `/api/devices/import` | 470 | `csv-import-dialog.tsx` (dialog นำเข้าด่วนในหน้า Devices) | ✅ มี | เฉพาะ device เท่านั้น |
| `/api/itam/devices/import` | 287 | **ไม่มีใครเรียกใช้เลย** | ✅ มี | โครงสร้างดีที่สุด แยก `device-import-contract.ts` (validation) + `device-import-persistence.ts` (write) ชัดเจน |

**ปัญหาสำคัญที่สุด:** endpoint ที่ผู้ใช้งานจริงเจอบ่อยที่สุด (`/api/import` ผ่านหน้า Import หลัก) **ไม่มี `db.$transaction`** ทำให้ถ้านำเข้าไฟล์ใหญ่แล้วเกิด error กลางทาง (แถวข้อมูลผิด format, timeout, memory) **ข้อมูลจะถูกเขียนเข้า DB ไปแล้วบางส่วนแบบกู้คืนไม่ได้** ผู้ใช้จะเห็นข้อมูลซ้ำ/ขาดหาย โดยไม่รู้ว่าแถวไหนเข้าไปแล้วบ้าง — ตรงกับอาการ "นำเข้าข้อมูลมีปัญหา" ที่สุด

**ปัญหารอง:** มี 2 UI ให้ผู้ใช้นำเข้า device ได้ (dialog ด่วน vs หน้า Import หลัก) ที่พฤติกรรม validation ไม่ตรงกัน (คนละไฟล์คนละ logic) ผู้ใช้อาจสับสนว่าทำไมนำเข้าทางหนึ่งผ่าน อีกทางหนึ่งไม่ผ่าน

### 2.3 แนวทางแก้ (Methodology)

**หลักการ: รวมเป็น pipeline เดียว ใช้ของที่ดีที่สุดที่มีอยู่แล้ว (`/api/itam/devices/import`) เป็นฐาน แทนที่จะเขียนใหม่ทั้งหมด**

**Phase A — หยุดเลือดก่อน (เร่งด่วน, ไม่ต้อง refactor ใหญ่)**
1. เพิ่ม `db.$transaction` ครอบส่วน device-import ใน `/api/import/route.ts` ทันที (แก้เฉพาะจุดเสี่ยง ไม่ต้องรอ refactor ทั้งไฟล์)
2. เพิ่ม batch size limit + progress feedback ถ้ายังไม่มี (ป้องกัน timeout กลางทางที่เป็นสาเหตุให้ transaction ยาวเกินไป)

**Phase B — รวม endpoint (งานหลัก)**
1. ทดสอบ `/api/itam/devices/import` (ตัวที่ไม่มีใครเรียกใช้) กับข้อมูลจริงของระบบก่อน — เช็คว่า `device-import-contract.ts` validate ครอบคลุมทุกเคสที่ `/api/import` เดิมรองรับหรือไม่ (เช่น การ update ทับของเดิม, การ map คอลัมน์ CSV ที่ชื่อไม่ตรง)
2. ถ้าครอบคลุมครบ → ปรับ `csv-import-dialog.tsx` และ `import-page.tsx` ให้เรียก `/api/itam/devices/import` แทนทั้งคู่
3. ย้าย logic ส่วน stock-in/stock-out ที่ปนอยู่ใน `/api/import` เดิม ออกมาเป็น endpoint เฉพาะทาง (`/api/stock/import` เป็นต้น) แยกจาก device import โดยสิ้นเชิง — ลดขนาดไฟล์ 2,336 บรรทัดให้จัดการง่ายขึ้น
4. Deprecate `/api/devices/import` (470 บรรทัด) และ `/api/import` เดิม หลังยืนยันว่า endpoint ใหม่ทำงานแทนได้ครบ 100% แล้วเท่านั้น (อย่าลบก่อนทดสอบขนานกันสักระยะ)

**Phase C — เพิ่มความน่าเชื่อถือ**
1. เพิ่ม "dry-run mode" (ตรวจไฟล์ก่อนนำเข้าจริง โชว์ preview ว่าจะ insert/update/error กี่แถว) ถ้ายังไม่มี
2. เพิ่ม import log/history table (เก็บว่าใครนำเข้าไฟล์ไหนเมื่อไหร่ กี่แถวสำเร็จ/ผิดพลาด) เพื่อ debug ย้อนหลังได้ง่ายขึ้นเวลาผู้ใช้แจ้งปัญหา

### 2.4 ความเสี่ยงที่ต้องระวัง
- ต้อง backfill/ทดสอบให้แน่ใจว่า endpoint ใหม่รองรับทุก column mapping ที่หน้าเก่าเคยรองรับ ก่อนตัดของเก่าทิ้ง (ทำคู่ขนานสัก 1-2 sprint ก่อนตัด)
- การเพิ่ม transaction ใน Phase A ต้องระวังเรื่อง timeout ของ transaction เอง (ถ้าไฟล์ใหญ่มาก transaction เดียวอาจ lock ตารางนานเกินไป) ควรแบ่งเป็น batch transaction ย่อยๆ แทนการทำทั้งไฟล์ในทีเดียว

### 2.5 ประมาณการความยาก
Phase A: งานเล็ก ทำได้เร็ว ควรทำก่อนสุด
Phase B: งานขนาดกลาง-ใหญ่ ต้องทดสอบเทียบพฤติกรรมเก่า-ใหม่ให้ละเอียด
Phase C: งานเสริม ทำเมื่อ A+B เสถียรแล้ว

สาเหตุแท้จริงที่ "รู้สึกไม่เข้าที่" น่าจะมาจากตัว `itam-settings.tsx` เอง: เป็นไฟล์เดียว 1,421 บรรทัดที่ยัด 16 แท็บไว้ด้วยกัน ทำให้แก้ไข/ทดสอบ/หา bug ยาก และ UX ของผู้ใช้ปลายทางอาจรู้สึกรกเพราะมีตัวเลือกเยอะเกินไปในที่เดียว

### 3.3 แนวทางแก้ (Methodology)

**หลักการ: ไม่ทิ้งของเก่า ไม่สลับไป v2 ตรงๆ แต่ทำ incremental refactor โดยยังคงฟีเจอร์ครบ 16 แท็บ**

**ขั้นตอนที่แนะนำ:**

1. **ตัดสินใจก่อน:** จะสาน `settings-page-v2.tsx` ต่อให้ครบ 16 พื้นที่ฟีเจอร์ (ใช้โครงสร้างแท็บที่สะอาดกว่าเป็นต้นแบบ) หรือจะ refactor `itam-settings.tsx` เดิมแบบค่อยเป็นค่อยไป — แนะนำแบบหลัง เพราะเสี่ยงน้อยกว่า (ของเดิมพิสูจน์แล้วว่าใช้งานได้จริงในทุกจุด)
2. **แยกไฟล์ทีละแท็บ:** ย้ายแต่ละ tab content ออกจาก `itam-settings.tsx` เป็นไฟล์ component แยก (เช่น `settings/master-data-tab.tsx`, `settings/site-attributes-tab.tsx` ฯลฯ) — คล้าย pattern ที่ `notification-templates-section.tsx` ทำอยู่แล้ว (แยกออกมาเป็นไฟล์ของตัวเองแล้ว) ใช้ pattern เดียวกันกับแท็บที่เหลือ
3. **จัดกลุ่มแท็บใหม่ตาม mental model ผู้ใช้** ไม่ใช่ตามลำดับที่พัฒนา — จากที่เห็นใน `SETTINGS_TAB_GROUPS` ปัจจุบันมี 4 กลุ่มอยู่แล้ว (ข้อมูล/ระบบ/การแจ้งเตือน/ปรับแต่ง) ซึ่งเป็นจุดเริ่มต้นที่ดี แค่ต้องเช็คว่าผู้ใช้จริงเข้าใจการจัดกลุ่มนี้หรือไม่ (แนะนำสอบถามผู้ใช้งานจริง/สังเกตพฤติกรรม)
4. **ลบ `settings-page-v2.tsx` ทิ้งถ้าตัดสินใจไม่สานต่อ** เพื่อไม่ให้ dev คนถัดไปสับสนว่าไฟล์ไหนคือของจริง (คอมเมนต์ไว้ก่อนลบจริงว่าทำไมถึงเลิกใช้ เผื่อมีคนกลับมาถามทีหลัง)

### 3.4 ความเสี่ยงที่ต้องระวัง
- การแยกไฟล์ต้องระวัง state ที่ share กันระหว่างแท็บ (เช่น ข้อมูล site ที่หลายแท็บใช้ร่วมกัน) ต้องยกขึ้นไปเป็น context หรือ query hook กลาง ไม่ใช่ prop drilling ลึกๆ

## ภาคผนวก: จุดอื่นที่ตรวจพบเพิ่มเติม (ยังไม่ได้ถูกร้องขอ แต่พบระหว่างสำรวจภาพรวมโปรเจกต์)

หลังสำรวจภาพรวมทั้งโปรเจกต์เพิ่มเติม (นอกเหนือจาก 3 หัวข้อหลักข้างต้น) พบ 3 จุดที่ควรวางแผนแก้ไข เรียงตามผลกระทบ:

### A. Test coverage เกือบเป็นศูนย์ (ความเสี่ยงเชิงระบบสูงสุด) — 🏷️ ✅ แก้แล้ว

**พบ:** โปรเจกต์มีไฟล์ source ทั้งหมด 556 ไฟล์ (.ts/.tsx ไม่รวม test) แต่มีไฟล์ทดสอบอัตโนมัติอยู่แค่ **1 ไฟล์เดียว** (`src/modules/reports/__tests__/service.test.ts`) คิดเป็นความครอบคลุมต่ำกว่า 1%

**ทำไมเรื่องนี้สำคัญกับแผนที่เสนอไปข้างต้น:** ทุกข้อเสนอในเอกสารนี้ (รวม endpoint นำเข้าข้อมูล, refactor หน้าตั้งค่า, แก้ webhook LINE OA) ล้วนเป็นการ "แก้ของที่ทำงานอยู่แล้ว" — โดยไม่มี automated test คอยเช็คว่าพฤติกรรมเดิมยังเหมือนเดิมหลังแก้ไข การ refactor แต่ละครั้งจึงเสี่ยงพังจุดที่ไม่ได้ตั้งใจแตะ (regression) โดยไม่มีใครรู้จนกว่าผู้ใช้จริงจะเจอ

**แนวทางแก้:**
1. ไม่ต้องเขียน test ครอบคลุมทั้งระบบทีเดียว (ทำไม่ไหวและไม่คุ้ม) — ให้เขียน test เฉพาะจุดที่กำลังจะแก้ไขใน 3 หัวข้อหลักของเอกสารนี้ก่อน (เช่น เขียน test ของ `/api/import` behavior เดิมไว้ก่อนเริ่ม refactor เพื่อจับ regression)
2. ตั้งกฎทีมง่ายๆ ว่า "โค้ดใหม่ทุกจุดที่แตะ business logic (ไม่ใช่ UI ล้วนๆ) ต้องมี test ควบคู่" แล้วค่อยๆ สะสม coverage ขึ้นไปตามงานที่ทำจริง ไม่ต้องรอทำทีเดียวครบ
3. เพิ่ม CI step รัน test อัตโนมัติตอน push/PR ถ้ายังไม่มี (เช็คว่ามี GitHub Actions/CI config ไหม ถ้าไม่มีควรเพิ่มพร้อมกัน)

### B. การแจ้งเตือน (LINE/Telegram/Email) ไม่มีการบันทึกผลส่ง/retry เมื่อล้มเหลว — 🏷️ ❌ ยังไม่แก้

**พบ:** ไม่มี model ฐานข้อมูลใดๆ เก็บประวัติการส่งแจ้งเตือน (`prisma/schema.prisma` ไม่มี model ที่เกี่ยวกับ notification log) ฟังก์ชันส่งใน `src/lib/notifications.ts` เป็นแบบ "ยิงแล้วลืม" — ถ้าส่งไม่สำเร็จ (LINE API rate limit, token หมดอายุ, network ขัดข้อง) จะแค่ `console.error` แล้วจบ ไม่มีการลองใหม่ ไม่มี record ให้แอดมินย้อนดูว่าแจ้งเตือนไหนหลุดไปบ้าง

**ผลกระทบจริง:** ถ้า LINE OA token หมดอายุกลางดึก การแจ้งเตือนงานด่วน/PM ที่ควรส่งไปหาช่างจะเงียบหายไปเฉยๆ โดยไม่มีใครรู้ จนกว่าจะมีคนสังเกตว่า "ทำไมช่างไม่มา"

**แนวทางแก้:**
1. เพิ่ม model `NotificationLog` (channel, target, payload, status: PENDING/SENT/FAILED, errorMessage, retryCount, sentAt)
2. ทุกครั้งที่เรียกฟังก์ชันส่ง ให้บันทึก record ก่อน แล้วอัปเดตสถานะหลังส่งเสร็จ/ล้มเหลว
3. เพิ่ม retry แบบง่าย (เช่น cron job ทุก 5-10 นาที ดึง record ที่ status=FAILED และ retryCount < 3 มาลองส่งใหม่)
4. เพิ่มหน้า/แท็บใน Settings ให้แอดมินดู log การแจ้งเตือนที่ล้มเหลวได้ (ผูกกับงาน refactor หน้าตั้งค่าที่เสนอไว้ในหัวข้อ 3 ได้เลย)

### C. ไม่มีการแจ้งเตือนอัตโนมัติสำหรับ PM ครบกำหนด และ License ใกล้หมดอายุ — 🏷️ ✅ แก้แล้ว

**พบ:** ตรวจ cron job ทั้ง 3 ตัวที่มีอยู่ (`daily-report`, `keepalive`, `sync-legacy`) พบว่า:
- ✅ **Warranty ใกล้หมดประกัน** — มีการเช็คอัตโนมัติใน `daily-report` (ภายใน 90 วัน)
- ❌ **PM Schedule ครบกำหนด** (`PMSchedule.lastRunDate`/`intervalDays`) — **ไม่มี cron ใดเช็คเลย** ทั้งที่ model มี field รองรับการคำนวณวันครบกำหนดครบ (`frequency`, `intervalDays`, `dayOfMonth`, `lastRunDate`)
- ❌ **License ใกล้หมดอายุ** (`LicenseRecord.Expiry_Date`) — **ไม่มี cron ใดเช็คเลย** เช่นกัน ทั้งที่มี field `Expiry_Date` พร้อมใช้งาน

**ผลกระทบ:** งาน PM (บำรุงรักษาเชิงป้องกัน) และการต่อ license จะพึ่งพาให้ staff เข้ามาเปิดหน้าดูเองเท่านั้น ไม่มีระบบเตือนเชิงรุก เสี่ยงลืมจนอุปกรณ์เสียก่อนเวลา หรือ license หมดอายุกะทันหันโดยไม่ทันตั้งงบต่อ

**แนวทางแก้:**
1. ขยาย `daily-report` cron (หรือสร้าง cron ใหม่) ให้เช็ค 2 เรื่องนี้เพิ่ม โดยใช้ pattern เดียวกับที่เช็ค warranty อยู่แล้ว (โครงสร้างโค้ดมีอยู่แล้ว แค่เพิ่ม query อีก 2 ก้อน)
2. กำหนดช่วงเวลาแจ้งเตือนล่วงหน้าที่เหมาะกับหน้างานจริง (เช่น PM แจ้งล่วงหน้า 7 วัน, License แจ้งล่วงหน้า 30-60 วัน ให้ทันตั้งงบประมาณต่อสัญญา)
3. ส่งแจ้งเตือนผ่านช่องทางเดียวกับที่มีอยู่แล้ว (LINE/Email ที่ตั้งค่าไว้ใน settings) — ใช้โครงสร้าง notification เดิม ไม่ต้องสร้างใหม่

### สรุปลำดับความสำคัญของภาคผนวก
1. **ข้อ C (PM/License alert)** — effort ต่ำที่สุด (ต่อยอดจากโค้ด warranty ที่มีอยู่แล้ว) ผลกระทบชัดเจน ทำก่อนได้เลย
2. **ข้อ B (Notification log/retry)** — effort ปานกลาง ป้องกันการสูญเสียการแจ้งเตือนแบบเงียบๆ
3. **ข้อ A (Test coverage)** — เป็นการลงทุนระยะยาว ควรเริ่มคู่ขนานไปกับทุกงาน refactor ที่เสนอในเอกสารนี้ ไม่ใช่ทำแยกเป็นโปรเจกต์เดี่ยว

## ภาคผนวก 2: ตรวจ 5 โมดูลเพิ่มเติมตามคำขอ (Sticker/QR, Accessories, Sites, Health/Sync-legacy, Mobile)

### D. 🔴 Sticker/QR Editor ไม่เชื่อมกับระบบ Smart QR Router — ปัญหารากฐานที่สุดในเอกสารนี้ — 🏷️ ✅ แก้แล้ว

**พบ:** `src/components/itam/itam-sticker-editor.tsx` สร้าง QR element โดย default ใช้ `{{AssetNo}}` (ข้อความรหัสทรัพย์สินธรรมดา) รายการตัวแปรทั้งหมด (`STICKER_VARIABLES` ใน `src/lib/sticker-template.ts`, 19 ตัว) **ไม่มีตัวแปรใดสร้าง URL ได้เลย** และ `StickerDeviceData` interface **ไม่มีแม้แต่ `device.id`** — ข้อมูลที่จำเป็นต่อการสร้างลิงก์ไม่ถูกส่งเข้ามาตั้งแต่ชั้น data fetching

**หลักฐานสำคัญที่สุด:** ในไฟล์ `src/lib/smart-qr.ts` มีฟังก์ชัน `generateStickerQrData(type, id, action, baseUrl)` ที่เขียน comment ระบุตรงตัวว่า `"Generate QR data for sticker printing (URL string to encode)"` — **สร้างไว้เพื่อจุดประสงค์นี้โดยเฉพาะ แต่ตรวจแล้วไม่มีไฟล์ไหนเรียกใช้ฟังก์ชันนี้เลยแม้แต่จุดเดียวในทั้งโปรเจกต์**

**ผลกระทบ:** สติกเกอร์ที่พิมพ์จากเครื่องมือนี้ เมื่อสแกนด้วยกล้องมือถือทั่วไป จะไม่เปิดหน้าเว็บใดๆ (ได้แค่ข้อความรหัสทรัพย์สิน) ทำให้ระบบ Smart QR Router + PublicReporter + tier verification ทั้งหมดที่ออกแบบไว้ก่อนหน้าในเอกสารนี้ **ใช้งานไม่ได้จริงกับสติกเกอร์จริงที่ติดอยู่บนอุปกรณ์** (ใช้ได้แค่ทางอ้อมผ่าน LINE OA แชทที่ถอดรหัสรูปแล้วจับคู่รหัสทรัพย์สินเป็น fallback เท่านั้น)

**แนวทางแก้ (effort ต่ำ เพราะของที่ต้องใช้มีอยู่แล้วครบ แค่ต้องต่อสาย):**
1. เพิ่ม `id: string` เข้า `StickerDeviceData` interface ใน `src/lib/sticker-template.ts`
2. เพิ่มตัวแปรใหม่ `{{QrUrl}}` เข้า `STICKER_VARIABLES` — ตอน render ให้เรียก `generateStickerQrData('d', device.id, 'repair')` ที่มีอยู่แล้วมาแทนที่ตัวแปรนี้
3. เปลี่ยนค่า default ของ QR element ใหม่ในเครื่องมือแก้ไข จาก `{{AssetNo}}` → `{{QrUrl}}`
4. **สำคัญ:** เทมเพลตสติกเกอร์เก่าที่มีอยู่แล้วในระบบ (ถ้าเคยสร้างไว้) ยังใช้ `{{AssetNo}}` อยู่ ต้องแจ้งเตือนผู้ใช้ให้ไปแก้เทมเพลตเดิม หรือเขียน migration script อัปเดต QR element ที่ยัง reference `{{AssetNo}}` ให้เป็น `{{QrUrl}}` อัตโนมัติ (ควรมี dry-run ให้ preview ก่อนเปลี่ยนจริง)
5. ทดสอบ end-to-end จริง: พิมพ์สติกเกอร์ตัวอย่าง 1 ใบ → สแกนด้วยกล้องมือถือปกติ (ไม่ใช่แอป LINE) → ต้องเปิดหน้า Smart QR Router ได้ถูกต้อง ก่อนจะประกาศว่าใช้งานได้จริง

**ระดับความสำคัญ:** ควรทำเป็นลำดับแรกสุดในทุกงานที่เกี่ยวกับ Smart QR/LINE OA ที่วางแผนไว้ก่อนหน้าในเอกสารนี้ เพราะ Phase 1-4 ของแผน LINE OA จะไม่มีความหมายถ้าสติกเกอร์จริงยังใช้งานไม่ได้

### E. Accessories module — ✅ ไม่พบปัญหา

### F. 🟠 Sites Management (sites / site-attributes / site-rates) — ยืนยัน bug จากตารางเก่าที่ตายแล้ว — 🏷️ ✅ แก้แล้ว

**พบ:** ระบบมีตาราง `Site` (legacy) ที่ตามคอมเมนต์ในโค้ดเอง (`src/app/api/sites/route.ts`) ระบุว่า **มี 0 แถวใน Supabase จริง** — ข้อมูลสาขาจริงทั้งหมดย้ายไปอยู่ที่ตาราง `SiteAttribute` แล้ว แต่ยังมี **3 endpoint ที่ query ตาราง `Site` เก่าอยู่**:

## ภาคผนวก 3: บั๊กการพิมพ์สติกเกอร์กับเครื่องพิมพ์ป้ายต่อเนื่อง (Continuous Label Printer)

### J. 🔴 ระบบสติกเกอร์ hardcode ขนาดกระดาษเป็น A4 — ใช้กับเครื่องพิมพ์ป้ายม้วนต่อเนื่องไม่ได้ — 🏷️ ✅ แก้แล้ว

**อาการที่ผู้ใช้เจอ:** สั่งพิมพ์สติกเกอร์ไปที่เครื่องพิมพ์ป้าย Brother PT-P950NW (เครื่องพิมพ์เทปม้วนต่อเนื่อง ความกว้าง 36mm) แล้วผลลัพธ์ไม่ตรงกับตัวอย่าง ต้องไปปรับ paper size/scale เองใน print dialog ทุกครั้งและก็ยังไม่ตรง

**สาเหตุที่ยืนยันจากโค้ด:** ทั้ง 2 จุดที่ generate HTML สำหรับพิมพ์สติกเกอร์ hardcode ค่า `@page` เป็น A4 ตายตัว:
```css
/* src/components/itam/sticker-print-dialog.tsx บรรทัด 670 */
@page { size: A4; margin: 10mm; }

/* src/lib/sticker-template.ts บรรทัด 547 */
@page { size: A4 ${orientation}; margin: ${margin}mm; }
```
ขนาดสติกเกอร์ที่เลือกได้ (`SIZE_OPTIONS`: เล็ก 50×30 / กลาง 70×40 / ใหญ่ 100×50 mm) เป็นแค่ขนาดกล่องเนื้อหาที่จัด grid บนแผ่น A4 (โมเดล "สติกเกอร์หลายดวงต่อแผ่นกระดาษ A4") — ไม่มีโหมดสำหรับเครื่องพิมพ์ป้ายม้วนต่อเนื่อง (Brother/Dymo/Zebra continuous label) ที่พิมพ์ทีละดวงต่อกันไปตามความกว้างเทปจริงเลย

**หลักฐานว่ามีวิธีทำที่ถูกต้องอยู่แล้วในโค้ดจุดอื่น:** `src/components/itam/template-editor.tsx` (บรรทัด 2151) ใช้ pattern ที่ถูกต้อง:
```css
@page { size: ${paper.width}mm ${paper.height}mm; margin: 0; }
```
คือกำหนดขนาดหน้าให้ตรงกับขนาดป้ายจริงแบบไดนามิกตามค่าที่ผู้ใช้ตั้ง — ควรนำ pattern นี้มาใช้กับสติกเกอร์แทนการ hardcode A4

**กลไกการพิมพ์ปัจจุบัน (สำหรับทีมที่จะแก้):** ฟังก์ชันสร้าง HTML (`buildPrintDocument` ใน `sticker-print-dialog.tsx`) สร้างเป็น string HTML สมบูรณ์ในตัวเอง (self-contained document พร้อม `<style>` ของตัวเอง) แล้วเปิด `window.open('', '_blank')` เขียน HTML เข้าไป แล้วเรียก `win.print()` — จุดแก้ไขจึงอยู่ที่การ generate ค่า `@page` ให้ไดนามิกตามโหมดที่เลือก ไม่ต้องรื้อกลไกการเปิดหน้าต่างพิมพ์ใหม่

### คำแนะนำสำหรับทีมพัฒนา (แนวทางแก้ ไม่ใช่โค้ดสำเร็จรูป)

**เป้าหมาย:** ให้ผู้ใช้เลือกได้ว่าเครื่องพิมพ์เป็น "กระดาษแผ่น A4 (หลายดวงต่อแผ่น)" หรือ "เครื่องพิมพ์ป้ายม้วนต่อเนื่อง (ทีละดวง)" แล้วระบบ generate เอกสารพิมพ์ให้ตรงกับโหมดนั้นจริง

1. **เพิ่ม printer mode selector ใน `sticker-print-dialog.tsx`** — เพิ่ม state ใหม่ เช่น `printerMode: 'sheet' | 'continuous'` แยกจาก `size` (ขนาดสติกเกอร์) ที่มีอยู่แล้ว เพราะทั้งสองเป็นคนละมิติกัน (ขนาดสติกเกอร์ vs รูปแบบกระดาษ)

2. **เมื่อเลือก `continuous`:**
   - ให้ผู้ใช้กรอก/เลือกความกว้างเทป (mm) เช่น dropdown ค่าที่พบบ่อย 12/18/24/29/36/50/62mm (ตามสเปกเทป Brother/Dymo ทั่วไป) หรือกรอกเองได้
   - `buildPrintDocument` ต้อง generate `@page { size: ${tapeWidthMM}mm auto; margin: 0; }` แทนการ fix เป็น A4 — สังเกตว่าใช้ `auto` สำหรับความสูง เพราะเทปม้วนต่อเนื่องไม่มีความยาวตายตัว ต่างจาก sheet mode ที่ทั้งกว้าง/สูงต้องระบุ (อ้างอิง pattern จาก `template-editor.tsx` แต่ปรับให้ height เป็น auto)
   - CSS `.grid`/`.page` ในโหมดนี้ต้องเปลี่ยนจาก grid หลายคอลัมน์ (สำหรับ A4) เป็น layout แนวตั้งทีละดวง ไม่มี gap ระหว่างดวงถ้าต้องการตัดต่อกันพอดี
   - ควรมี CSS `body { width: ${tapeWidthMM}mm }` กำกับด้วย เพื่อกันเนื้อหาล้นความกว้างเทปจริง (ป้องกันข้อความ/QR ถูกครอปที่ขอบ)

3. **เมื่อเลือก `sheet` (ของเดิม):** ใช้ logic เดิมทั้งหมด ไม่ต้องแตะ — เพื่อไม่ให้กระทบผู้ใช้ที่พิมพ์บนกระดาษ A4 อยู่แล้ว

4. **หมายเหตุสำคัญสำหรับทีม QA:** ต้องทดสอบพิมพ์จริงกับเครื่องพิมพ์ป้ายจริงอย่างน้อย 1 รุ่น (ไม่ใช่แค่ดู print preview ในเบราว์เซอร์) เพราะพฤติกรรมการตีความ `@page size` กับกระดาษที่ไม่ใช่ A4/Letter อาจต่างกันไปตาม driver ของเครื่องพิมพ์แต่ละยี่ห้อ/ระบบปฏิบัติการ (Windows print driver ของ Brother มักมี custom paper size ของตัวเองอยู่แล้ว ต้องเช็คว่า CSS `@page size` ที่ส่งไปสอดคล้องกับ driver settings หรือจะขัดกัน)

5. **ผูกกับภาคผนวก 2 ข้อ D (Sticker QR ไม่เชื่อมกับ Smart QR Router):** แนะนำให้ทีมแก้ 2 เรื่องนี้พร้อมกันในรอบเดียว เพราะเป็นไฟล์/ฟีเจอร์เดียวกัน (ระบบพิมพ์สติกเกอร์) จะได้ทดสอบ end-to-end ครบทั้งเนื้อหา QR ที่ถูกต้อง และขนาดกระดาษที่ถูกต้องไปพร้อมกัน ลดรอบการทดสอบซ้ำ

### L. 🟡 Meter Reading — ระบบดีมาก แต่ไม่มีกลไก "Amendment" ตามที่ออกแบบไว้ — 🏷️ ❌ ยังไม่แก้ (ไม่เร่งด่วน)

**ยืนยันแล้วว่าโมดูลนี้ออกแบบดีที่สุดจุดหนึ่งในระบบ:**
- `MeterReading` เป็น append-only (ไม่มี PATCH/DELETE endpoint เลย)
- มี `isMeterDecreased()` บังคับ flow ยืนยัน 2 ขั้นตอน (HTTP 409 + `confirmReset` + ต้องกรอกหมายเหตุ) เมื่อค่ามิเตอร์ลดลงผิดปกติ ป้องกันการ reset มิเตอร์แบบไม่ตั้งใจ/ไม่มีการบันทึก
- ตอนปิดรอบบิล (`Cycle` → CLOSED) จะสร้าง **immutable snapshot แบบ SHA-256 hash** ของข้อมูลมิเตอร์ทั้งหมดในรอบนั้น ป้องกันการแก้ไขย้อนหลังแบบเงียบๆ

**จุดที่ยังขาด:** โค้ดใน `src/lib/meter-snapshot.ts` มี comment อธิบาย design ของ **"Amendment"** (กลไกแก้ไขแบบมีการควบคุม สร้าง snapshot revision ใหม่เฉพาะจุดที่แก้ พร้อม audit trail ผ่าน model `MeterReportAmendment`) ไว้ชัดเจนว่าเป็นส่วนหนึ่งของ lifecycle ที่ตั้งใจสร้าง **แต่ตรวจ `prisma/schema.prisma` แล้วไม่มี model `MeterReportAmendment` อยู่จริง และไม่มี endpoint ใดๆ ที่ implement กลไกนี้เลย**

**ผลกระทบ:** ถ้าพบว่ามิเตอร์ 1 รายการในรอบที่ปิดไปแล้วบันทึกผิด (เช่น กดเลขผิด) วิธีเดียวที่มีตอนนี้คือ **reopen ทั้งรอบ** (กระทบข้อมูลทั้งเดือนทั้งไซต์ ไม่ใช่แค่รายการที่ผิด) ซึ่งกว้างเกินความจำเป็นและเสี่ยงเปิดช่องให้แก้รายการอื่นที่ไม่ได้ตั้งใจไปด้วย

**แนวทางแก้ (งานระยะกลาง ไม่เร่งด่วนเท่าข้อ K แต่ควรวางแผนไว้):**
1. เพิ่ม model `MeterReportAmendment` ตาม design ที่ comment ไว้แล้ว (มี field: เดือนที่แก้, รายการมิเตอร์ที่แก้, ค่าเดิม/ค่าใหม่, เหตุผล, ผู้แก้, revision อ้างอิง)
2. สร้าง endpoint ใหม่ (เช่น `POST /api/cycles/[id]/amendments`) ที่รับการแก้ไขเฉพาะรายการ แล้วสร้าง snapshot revision ใหม่ (`createMeterReportSnapshot` ที่มีอยู่แล้วรองรับ revision number อยู่แล้ว — ใช้ต่อได้เลย) โดยไม่ต้อง reopen ทั้งรอบ
3. จำกัดสิทธิ์ endpoint นี้ให้แคบกว่า `METER_WRITE` ทั่วไป (เช่น permission ใหม่ `METER_AMEND` ให้เฉพาะ admin/manager) เพราะเป็น action ที่กระทบข้อมูลการเงินที่ปิดรอบไปแล้ว

### M. 🟡 Licenses — ไม่มีหน้าจัดการภาพรวม ผูกกับ device เท่านั้น — 🏷️ ✅ แก้แล้ว

1. ผ่าน `device-detail-sheet.tsx` (ดู/เพิ่ม license ทีละเครื่อง ต้องรู้ว่า license นั้นผูกกับอุปกรณ์ไหนก่อน)
2. Import/Export เป็น CSV ทั้งชุด (`/api/licenses/import`, `/api/licenses/export`)

**ผลกระทบ:** ไม่มีทางดู "license ทั้งหมดที่ใกล้หมดอายุข้ามทุกอุปกรณ์" ในหน้าเดียวได้เลย ต้องเปิดทีละอุปกรณ์ หรือ export CSV มาเปิดดูเองใน Excel — ประกอบกับที่พบในภาคผนวก 1 ว่าไม่มี cron แจ้งเตือน license ใกล้หมดอายุด้วย **สรุปคือระบบติดตาม license อ่อนทั้ง 2 ชั้น (ไม่มีทั้ง proactive alert และไม่มีทั้ง central view)**

**แนวทางแก้:** สร้างหน้า licenses-page.tsx ใหม่ (ตาราง license ทั้งหมด + filter ใกล้หมดอายุ + ค้นหาข้ามอุปกรณ์) ควรทำคู่กับการเพิ่ม cron แจ้งเตือนใน Appendix 1 ข้อ C เพราะเป็นฟีเจอร์ที่เสริมกัน

### N. 🔴 Cost Analytics — บั๊กคำนวณต้นทุน: หน้าขาว-ดำและสีถูกคิดราคาเดียวกันหมด (ใช้ราคา BW กับทุกหน้า) — 🏷️ ❌ ยังไม่แก้ (ตรวจซ้ำ 2 รอบ ยืนยันบั๊กเดิม — แนะนำทำก่อน)

**พบ:** `src/app/api/cost-analytics/route.ts` บรรทัด 84-114:
```ts
const rateMap = new Map(rates.map((r) => [r.siteCode, r.bwRate]))   // ← ดึงมาแค่ bwRate
...
const sheets = (r.pagesBw ?? 0) + (r.pagesColor ?? 0)                 // ← รวมหน้าขาวดำ+สีเข้าด้วยกัน
const rate = rateMap.get(d.site) ?? defaultRate                      // ← rate ที่ได้คือ bwRate เท่านั้น
const cost = Math.round(sheets * rate * 100) / 100                   // ← เอาหน้ารวมคูณราคา BW ราคาเดียว
```
**ผลคือหน้าพิมพ์สีทั้งหมดถูกคิดราคาเท่ากับหน้าขาวดำ** ทั้งที่ในระบบ (`SiteRate` model) มี `colorRate` แยกไว้ต่างหากอยู่แล้ว และปกติราคาต่อหน้าสีจะสูงกว่าขาวดำมาก (ตัวอย่างจากคอมเมนต์ในโค้ดจุดอื่นของระบบเอง: BW 0.5 บาท/หน้า vs Color 5 บาท/หน้า — ต่างกันถึง 10 เท่า) **แปลว่าหน้า Cost Analytics นี้คำนวณต้นทุนต่ำกว่าความเป็นจริงอย่างมีนัยสำคัญสำหรับสถานที่ที่มีการพิมพ์สีเยอะ**

**หลักฐานยืนยันว่ามีวิธีทำถูกต้องอยู่แล้วในระบบเดียวกัน:** `src/modules/reports/unified-report-builder.ts` (โมดูลรายงานอีกจุดหนึ่ง) แยกคำนวณ `totalBwCost` และ `totalColorCost` โดยใช้ `bwRate`/`colorRate` แยกกันอย่างถูกต้อง ตามคอมเมนต์ในโค้ดเองระบุว่า `"totalCost now uses per-site SiteAttribute rates instead of hardcoded 0.5/5 baht/page. This is the actual billable amount."` — ยืนยันว่าทีมเคยแก้ปัญหานี้ถูกต้องในจุดหนึ่งแล้ว แต่ไม่ได้เอา fix เดียวกันไปใช้กับ `cost-analytics/route.ts` ด้วย

**แนวทางแก้:**
1. แก้ `rateMap` ให้เก็บทั้ง `bwRate` และ `colorRate` (เช่น เปลี่ยนเป็น `Map<siteCode, {bw: number, color: number}>`)
2. แยกคำนวณ `cost = pagesBw * bwRate + pagesColor * colorRate` แทนการรวมหน้าก่อนคูณ
3. แปลง Prisma `Decimal` เป็น number อย่างชัดเจนด้วย `.toNumber()` ก่อนคำนวณเสมอ (ตอนนี้พึ่งพา implicit coercion ของ Decimal.js ซึ่งใช้ได้แต่ควรเขียนให้ชัดเจนกว่านี้ ป้องกันปัญหาถ้าเปลี่ยนเวอร์ชัน Prisma ในอนาคต)
4. เขียน unit test เทียบผลลัพธ์ cost-analytics กับ unified-report-builder สำหรับข้อมูลชุดเดียวกัน ควรได้ตัวเลขต้นทุนรวมตรงกัน — ใช้เป็น regression test กันบั๊กแบบนี้เกิดซ้ำในโมดูลอื่นที่อาจมี pattern เดียวกัน

**ระดับความสำคัญ:** สูง เพราะกระทบตัวเลขที่ผู้บริหารใช้ตัดสินใจเรื่องงบประมาณจริง ควรแก้เร็วรองจากข้อ K

### P. 🏷️ ⏸️ รอข้อมูลเพิ่มเติม — Sticker: ขนาด Preview Modal ไม่ระบุ width/height ตาม canvas

**พบระหว่างตรวจ:** popup "พรีวิวสติกเกอร์" (`previewOpen` dialog ใน `itam-sticker-editor.tsx`) ไม่ได้กำหนด width/height ของ wrapper ตาม `paperWidth`/`paperHeight` ที่ API คืนมา — ใช้แค่ container ทั่วไปที่มี padding คงที่ ต่างจาก HTML ที่คืนมาซึ่งมี inline `width/height` เป็น mm ระบุไว้อยู่แล้วในตัว `<div class="stk-sticker">`
